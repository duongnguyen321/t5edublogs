# Pact Contract Testing cho Microservices: Từ Interaction đến can-i-deploy

> Pact contract testing giúp team kiểm tra compatibility giữa consumer và provider trước khi hai service phải chạy cùng nhau trong một môi trường integration đầy đủ. Bài này dành cho QA automation engineer, SDET và developer/tester đã biết HTTP, API testing, unit test, integration test và CI, muốn thiết kế contract test có scope đúng thay vì biến Pact thành một bộ integration test khác.

## Vì sao Pact không phải là integration test thu nhỏ?

Trong một hệ thống microservices, consumer gọi provider qua HTTP hoặc message broker. Consumer không cần biết toàn bộ implementation bên trong provider, nhưng nó có những giả định cụ thể: endpoint nào được gọi, method nào được dùng, header nào cần có, status code nào được xử lý và field nào phải tồn tại trong response.

Contract testing kiểm tra chính vùng giao tiếp đó. Consumer viết một interaction mô tả request và response mà nó thực sự cần. Pact biến các interaction thành pact file. Provider lấy pact file để verification trên một instance có thể kiểm soát được. Nếu provider đổi `customerId` thành `customer_id`, xóa một field hoặc đổi status code làm consumer không còn xử lý được, contract verification có thể phát hiện trước khi release.

Điểm quan trọng là contract test không trả lời câu hỏi “provider có đúng toàn bộ business rule không?”. Đó là phạm vi của functional test phía provider. Pact trả lời câu hỏi hẹp hơn: “provider có còn tương thích với cách consumer đang sử dụng nó không?”. [Pact consumer guide](https://docs.pact.io/consumer) cũng khuyến nghị chỉ assert những thay đổi thực sự ảnh hưởng đến consumer, tránh biến contract thành một schema khổng lồ và brittle.

| Loại kiểm thử | Câu hỏi chính | Môi trường thường dùng | Rủi ro nếu dùng sai |
|---|---|---|---|
| Unit test | Một hàm hoặc class có xử lý đúng không? | Isolated process | Không phát hiện sai mapping với API thật |
| Contract test | Hai bên còn tương thích không? | Consumer mock và provider local/CI | Contract quá chặt hoặc thiếu scenario quan trọng |
| Integration test | Nhiều thành phần chạy cùng nhau có đúng không? | Shared hoặc ephemeral environment | Chậm, khó setup và khó triage |
| Functional test | Provider có thực hiện đúng nghiệp vụ không? | Provider test environment | Có thể bị nhầm scope với contract test |

## Pact interaction gồm những phần nào?

Một interaction là một scenario độc lập giữa consumer và provider. Nó thường có provider state, mô tả dễ đọc, request và response expectation. Ví dụ, consumer gọi `GET /orders/88` khi order tồn tại. Contract không chỉ lưu path. Nó còn mô tả method, header cần thiết, status và những phần response mà consumer sẽ đọc.

Provider state không phải là bước chạy trước đó trong một test flow dài. Mỗi interaction được verify độc lập. Vì vậy, state “order 88 tồn tại” phải được provider dựng lại trước interaction bằng fixture, factory hoặc database seed. Không nên phụ thuộc vào một interaction khác đã tạo dữ liệu trước đó, vì điều này làm verification khó chạy song song và khó lặp lại.

Trong JavaScript hoặc TypeScript, team thường đặt Pact test gần API client, không đặt ở UI test. Test nên gọi class hoặc function chịu trách nhiệm tạo HTTP request. Cách này cho biết chính xác consumer gửi gì và nhận gì, đồng thời tránh kéo toàn bộ UI flow vào mock server.

```ts
import { PactV4 } from '@pact-foundation/pact';

const provider = new PactV4({
  consumer: 'CheckoutWeb',
  provider: 'OrderApi',
});

it('gets an order that can be rendered by checkout', async () => {
  await provider
    .addInteraction()
    .given('an order with id 88 exists')
    .uponReceiving('a request to get order 88')
    .withRequest('GET', '/orders/88', (request) => {
      request.headers({ Accept: 'application/json' });
    })
    .willRespondWith(200, (response) => {
      response.headers({ 'Content-Type': 'application/json' });
      response.jsonBody({
        id: 88,
        status: 'confirmed',
        total: 129000,
      });
    })
    .executeTest(async (mockServer) => {
      const client = new OrderClient(mockServer.url);
      const order = await client.getById(88);

      expect(order.id).toBe(88);
      expect(order.status).toBe('confirmed');
    });
});
```

Đoạn test trên không chứng minh order service tính tổng tiền đúng. Nó chứng minh client gửi request theo cách provider hiểu và client có thể deserialize response cần thiết. Nếu `total` chỉ được hiển thị nguyên dạng, expectation có thể dùng type matcher thay vì khóa một con số cụ thể.

## Chọn matcher thế nào để contract không brittle?

Sai lầm phổ biến là ghi lại một response lớn rồi exact-match mọi field. Cách này tạo cảm giác coverage cao nhưng lại khiến provider không thể thêm hoặc thay đổi field không liên quan. Consumer nên assert đúng những gì nó sử dụng.

Nếu consumer chỉ cần biết `id` là số và `status` là chuỗi thuộc tập mà nó xử lý, hãy dùng type hoặc value matcher phù hợp. Nếu consumer thực sự phụ thuộc vào `status: "confirmed"` để quyết định hiển thị nút thanh toán, giá trị đó cần được assert cụ thể. Nếu một field chỉ xuất hiện trong fixture nhưng không được consumer đọc, không nên đưa nó thành dependency chỉ vì response mẫu có field đó.

| Dữ liệu trong response | Cách assert phù hợp | Lý do |
|---|---|---|
| ID được parse thành number | Type matcher | Giá trị cụ thể thay đổi giữa môi trường |
| Status kích hoạt branch trong consumer | Exact hoặc regex có chủ đích | Thay đổi có thể làm consumer sai behavior |
| Timestamp chỉ cần parse được | Date hoặc format matcher | Không khóa thời điểm chạy test |
| Field không được consumer đọc | Không assert | Không tạo dependency thừa |
| Array cần ít nhất một phần tử | Type hoặc array matcher | Tránh khóa thứ tự và dữ liệu không liên quan |

[Pact documentation](https://docs.pact.io/consumer) nhấn mạnh rằng matching phải phản ánh compatibility boundary. Nếu tester dùng regex để kiểm tra business rule của provider, hoặc exact-match một payload khổng lồ để “cho chắc”, contract đang mở rộng ra ngoài nhiệm vụ của nó.

## Provider verification và consumer test khác nhau ra sao?

Consumer test tạo pact bằng mock provider. Nó kiểm tra API client của consumer có tạo request đúng và xử lý response đúng không. Provider verification chạy pact đó trên provider thật hoặc instance local của provider, rồi kiểm tra provider có đáp ứng từng interaction không.

Hai phía bổ sung cho nhau. Chỉ chạy consumer test thì contract có thể phản ánh một expectation mà provider không đáp ứng. Chỉ chạy provider verification với pact cũ thì team có thể không biết consumer vừa thêm một expectation mới. Vì vậy, pact file cần được publish và version hóa trong một flow mà cả hai team đều nhìn thấy.

Theo [Pact provider guidance](https://docs.pact.io/provider), verification nên chạy trên provider local hoặc trong CI, với downstream dependency được stub ở lớp phù hợp. Verify trực tiếp một provider đã deploy có thể làm feedback chậm, khó kiểm soát state và mất lợi ích của việc kiểm thử sớm. Điều này không có nghĩa deployed verification vô dụng, nhưng nó không nên là đường duy nhất để trả lời compatibility trước deploy.

Provider state cũng là điểm cần triage kỹ. Nếu verification fail vì fixture không tạo được state, đó chưa chắc là breaking change trong API. Log cần phân biệt ít nhất ba nhóm: request mismatch, response mismatch và state/setup failure. Nếu không phân biệt, team dễ sửa contract để che một lỗi test data.

## Pact Broker và can-i-deploy biến contract thành quality gate thế nào?

Pact file nằm trong một branch riêng chưa đủ để điều phối nhiều consumer và provider. Một Pact Broker lưu contract, version, branch hoặc tag và kết quả verification. Consumer publish pact sau khi test pass. Provider lấy các pact phù hợp để verify rồi publish verification result trở lại broker.

Bước có giá trị nhất trong deployment flow là compatibility check. Trước khi deploy một version consumer hoặc provider, `can-i-deploy` hỏi broker liệu version đó đã được verify với các version còn lại hay chưa. Nếu chưa, pipeline dừng thay vì suy đoán rằng hai service sẽ tương thích.

Một flow thực tế có thể đi theo thứ tự sau:

![A wide 21:9 educational CI/CD quality gate diagram for Pact Broker and can-i-deploy, showing Consumer CI publishing a pact, Provider CI verifying it, Pact Broker storing versions and verification results, then a deployment gate marked “can-i-deploy”, Vietnamese labels “Publish”, “Verify”, “Broker”, “Compatibility”, “Deploy”, T5Edu visual style matching the reference cover, navy #0B1F3A, electric blue #2563EB, violet #7C3AED, mint #14B8A6, warm yellow #FBBF24, clean vector layout with arrows and check marks, no people, no logos, no watermark, no photorealism, no excessive text](https://files.manuscdn.com/user_upload_by_module/session_file/310519663091035343/gXbyPaShJWjIdHwz.png)

1. Consumer chạy Pact test và publish pact với version commit hiện tại.
2. Provider CI lấy các pact chưa được verify, dựng provider local và chạy verification.
3. Provider publish kết quả pass hoặc fail lên Broker.
4. Pipeline của service sắp deploy chạy compatibility check.
5. Chỉ khi dependency graph phù hợp, pipeline mới tiếp tục deploy.

GOV.UK mô tả một workflow tương tự trong [tài liệu Pact Testing](https://docs.publishing.service.gov.uk/manual/pact-testing.html): consumer tạo pact file, publish lên broker, provider verify và các build tích hợp verification vào CI. Đây là case study thực tế để tham khảo, nhưng team vẫn cần kiểm tra version và khả năng hỗ trợ của implementation mình dùng.

### Khi nào Pact không phải lựa chọn tốt?

Pact không thay thế functional test của provider, end-to-end test của UI hoặc kiểm thử hiệu năng. Nếu team chỉ có một ứng dụng đơn khối và không có boundary giữa consumer với provider, chi phí duy trì broker có thể không đáng. Nếu consumer test chạy qua toàn bộ UI, interaction sẽ khó đọc và dễ tạo hàng trăm expectation trùng lặp.

### Có cần Pact khi đã có OpenAPI schema không?

OpenAPI mô tả API theo schema hoặc documentation contract. Pact bổ sung góc nhìn consumer: consumer thực sự dùng interaction nào và provider có verify được những expectation đó không. Hai loại artifact có thể cùng tồn tại, nhưng không nên tạo hai nguồn sự thật mâu thuẫn.

### Pact có thay thế integration test không?

Không. Pact kiểm tra compatibility của boundary trong môi trường nhẹ hơn. Integration test vẫn cần kiểm tra wiring, database, message broker và behavior khi nhiều thành phần chạy cùng nhau. Mục tiêu là dùng mỗi lớp cho câu hỏi phù hợp, không chọn một công cụ để thay tất cả.

## Triage Pact failure theo evidence, không sửa mù

Khi Pact verification fail, trước hết lưu request, response thực tế, interaction đang fail, provider state và commit của consumer/provider. Sau đó phân loại theo bảng sau.

| Failure | Dấu hiệu | Hướng điều tra đầu tiên |
|---|---|---|
| Request mismatch | Method, path, query hoặc header khác expectation | Kiểm tra API client và matcher request |
| Response mismatch | Status, header hoặc body không tương thích | Xác định provider breaking change hay expectation sai |
| State failure | Không dựng được dữ liệu cho provider state | Kiểm tra fixture, seed và dependency stub |
| Pact không được chọn | Broker không tìm thấy version phù hợp | Kiểm tra branch, tag, consumer version và publish step |
| can-i-deploy fail | Chưa có verification tương ứng | Đọc matrix compatibility thay vì bỏ qua gate |

Một lỗi contract không tự động có nghĩa provider sai. Consumer có thể đang assert field không dùng, dùng matcher quá chặt hoặc mô tả scenario không đúng nghiệp vụ. Ngược lại, nếu provider xóa field mà consumer thực sự parse, việc sửa consumer test để bỏ assertion là che lỗi. Triage tốt phải trả lời: dependency nào đã thay đổi, ai sở hữu dependency đó và test nào chứng minh thay đổi có chủ đích.

## Checklist thiết kế Pact contract cho team JS/TS

Trước khi merge contract test, hãy kiểm tra interaction có xuất phát từ API client thực tế hay không. Mỗi scenario cần có provider state tái lập được, mô tả dễ đọc và expectation chỉ bao phủ dữ liệu consumer sử dụng. Matcher phải đủ lỏng để provider tiến hóa an toàn, nhưng đủ chặt để bắt breaking change thật.

Ở provider, verification phải chạy trong CI trên instance có thể kiểm soát. Downstream dependency cần được stub đúng lớp, không stub trước khi request body được parse và validate. Broker phải lưu version và verification result có thể truy vết về commit. Deployment pipeline phải dùng compatibility check thay vì chỉ kiểm tra test local của một service.

Cuối cùng, hãy đo chất lượng contract bằng failure hữu ích, không bằng số interaction. Một contract nhỏ bắt đúng breaking change có giá trị hơn một pact file lớn khóa mọi chi tiết response.

## Tổng kết

Pact contract testing là lớp kiểm thử compatibility giữa consumer và provider, không phải functional test của provider và cũng không phải integration test thu nhỏ. Giá trị của Pact đến từ boundary rõ, interaction độc lập, matcher có chủ đích và provider verification chạy được trong CI.

Nếu team đang tích hợp nhiều API hoặc microservices bằng JavaScript/TypeScript, hãy bắt đầu từ một API client quan trọng, viết một interaction có provider state rõ ràng, rồi mới mở rộng sang Pact Broker và `can-i-deploy`. Nếu muốn củng cố nền tảng trước khi đi vào contract testing, bạn có thể xem thêm [Hướng dẫn API Testing cho người mới](/blogs/18-huong-dan-api-testing-cho-nguoi-moi) và [Cách khắc phục flaky test cho SDET](/blogs/19-khac-phuc-flaky-test-trong-automation).

Câu hỏi mở: trong hệ thống của bạn, boundary nào có rủi ro breaking change cao nhất nhưng hiện vẫn chỉ được bảo vệ bằng integration test thủ công?
